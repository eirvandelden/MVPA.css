## Round 1 — 2026-11-25T10:34Z — c07a881

Suite at review time: `bundle exec rake test` 425 runs, 0 failures; `rubocop`, `yamllint --strict .` and `npm run lint:css` clean. No `REVIEW.md` in the repository, so the reviewer's default passes ran (Bugs, Security, Compliance, Design).

- [ ] Important: `Release#upgrading` keeps only lines that match `^\d+\. (.+)$` and drops every other line of a fragment's `### Upgrading` section without a warning. A step that continues on a second line, carries a nested bullet, or shows a fenced markup snippet (the kind of example `CHANGELOG.md` and the README already use) loses that text in `CHANGELOG.md` and in the GitHub release, and these are the instructions an app needs to upgrade. Fragment validation only checks that `1. ` exists, so nothing catches it. Either keep each step's continuation lines while renumbering, or make `Fragment.read` refuse an Upgrading section with lines that are not numbered steps — `script/semver/release.rb:41` → fixed (Validate fragments strictly and keep the lines of an Upgrading step)
- [ ] Important: the release job exports `GH_TOKEN` (a `contents: write` token that can push to `main` and create tags) at job level, so every step sees it, including `spinel-coop/setup-rv@main`, a third-party action on a mutable branch ref that also runs `bundle install`. A change to that branch then runs with write access to this repository. Move `GH_TOKEN` to the `Release what merged` step and pin `setup-rv` to a commit SHA in this workflow (Dependabot updates SHA pins) — `.github/workflows/release.yml:20` → fixed (Give the release token to one step and pin setup-rv to a commit)
- [ ] Important: Compliance — the Proof list names the acceptance test `test/semver/release_acceptance_test.rb` `test_two_fragments_release_one_major_version` (order of work step 1), and neither the file nor the test exists. The behaviour is covered by `test_the_highest_level_wins` in `test/semver/release_test.rb:17`, so either add the named acceptance test or update the Proof line to the test that proves it — `docs/changes/adopt-semver/plan.md:440` → fixed (Add the acceptance test for one release from two fragments)
- [ ] Nit: Design — `Semver::PullRequest` (the class that decides a PR's level and refuses edited fragments) is not in `### Signatures`, and neither are the public helpers `Fragment.split`, `Fragment.sections_of`, `Fragment#validate`, `SurfaceChange.surface`, `Stamp.version_in`, `Stamp::CHECKS` and `Rules.tokens/files/selectors/pins/stylesheets/preludes`. Add `PullRequest` to the plan's signatures, and make the helpers `private_class_method` or private where nothing outside calls them — `script/semver/pull_request.rb:3` → fixed (Make the rule and surface helpers private)
- [ ] Nit: `script/semver/release` prints `released <version>` even when `publish` released nothing (tip is a release commit, or `unreleased?` is false), so a no-op rerun reads in the Actions log as a release of the current version — `script/semver/release:6` → fixed (Say when a release run released nothing)
- [ ] Nit: a non-Hash `overrides` value (`overrides: token` or `overrides: [token]`) raises `NoMethodError`/`TypeError` instead of `Fragment::Invalid`, so `PullRequest#verdict` does not rescue it and the Surface check fails with a stack trace instead of the fragment path and reason; the same holds for a front matter that is a list — `script/semver/fragment.rb:47` → fixed (Validate fragments strictly and keep the lines of an Upgrading step)
- [ ] Nit: `Fragment.sections_of` silently drops text before the first `###` heading and keeps only the last of two identical headings, and a fragment with no section at all is valid, so a release can stamp an entry with only its version heading — `script/semver/fragment.rb:26` → fixed (Validate fragments strictly and keep the lines of an Upgrading step)
- [ ] Nit: the uncommitted `Gemfile.lock` mixes the change this branch needs (`mvpa-css (6.0.0)`, matching the new `VERSION` literal) with an unrelated `rubocop-eirvandelden` 0.1.0 → 1.0.0 and `rubocop-rbs_inline` change. Commit only the `mvpa-css` lines here, or leave the lock out; note too that release commits never touch `Gemfile.lock`, so every release leaves its `mvpa-css` version stale and `bi` dirties it — `Gemfile.lock:20` → fixed (Lock the mvpa-css version that version.rb now declares)

- [ ] Important: the first release can never ship. The release job runs `bundle exec rake test` on the stamped tree before it pushes (`Stamp::CHECKS`), and `test_every_entry_heading_starts_with_a_version` asserts exactly 15 `## ` headings in `CHANGELOG.md`. The release adds a 16th heading, so the test fails, `attempt` rolls back and re-raises, and every later run fails the same way. Reproduced: stamping `changelog.d/adopt-semver.md` into a copy of HEAD as 7.0.0 and running `test/changelog_upgrading_test.rb` gives `Expected: 15 Actual: 16`. Assert the 15 retroactive entries (for example, every heading matches the format and the entries up to `6.0.0 - 2026-11-11` count 15) instead of the total, and add a test that runs the changelog assertions against a stamped `CHANGELOG.md` so a future count or order assertion cannot block releases again — `test/changelog_upgrading_test.rb:117` → fixed (Let a new release pass the changelog tests)
- [ ] Nit: each release leaves `Gemfile.lock` stale on `main`. The release job's `bundle exec rake test` rewrites the lock's `mvpa-css (6.0.0)` to the new version (seen in the same reproduction), but `git add *Stamp::PATHS` leaves the lock out, so after 7.0.0 `main` locks 6.0.0 while `version.rb` says 7.0.0 and every `bi` dirties the lock. Round 1's fix locked 6.0.0 only. Add `Gemfile.lock` to the stamped paths after the checks ran, or note in the plan why it stays stale — `script/semver/stamp.rb:6` → dismissed: stamping Gemfile.lock would add a fourth path to the release commit, which the accepted plan keeps to three, and risks committing bundler's other lock rewrites; Bundler re-resolves the line, consumers do not read this lockfile, and the plan's Risks now records it
- [ ] Nit: the write token still reaches the steps before the release step. `actions/checkout` persists the job's `GITHUB_TOKEN` (`contents: write`) for later git calls by default, so `setup-rv`'s `rv ci` and any gem install hook can read it. The pin closes the mutable-ref risk, but the Proof line "The write token reaches one step" overstates what `test_the_token_reaches_only_the_release_step` checks. Either reword that Proof line and the design decision, or set `persist-credentials: false` and give the release step's `git push` its credential from `GH_TOKEN` — `.github/workflows/release.yml:20` → fixed (Keep the write token away from the steps before the release)
